# TeamUp · 项目组队与成员招募平台

面向「有项目想法却找不到队友、想参加项目却不了解任务和要求」的学生场景：发起人公开项目目标和所需角色，其他用户按兴趣与技能查找项目、申请加入，发起人审核后形成成员名单和招募状态。

- 前端（端口 3000）：React 18 + Vite + React Router
- 后端（端口 3001）：Node.js + Express + better-sqlite3
- 数据库：SQLite，文件位于容器内 `/app/data/teamup.db`（通过 `./backend/data` 卷持久化）
- 部署：Docker Compose，`docker compose up --build` 一键启动

## 1. 快速开始

前置要求：已安装 Docker 与 Docker Compose（含 Linux 容器支持）。

```bash
cd teamup
docker compose up --build
```

启动后：

- 前端页面：http://localhost:3000
- 后端接口：http://localhost:3001 （健康检查 `GET /api/health`）

首次启动时后端会自动执行 `seed.js` 初始化示例数据（幂等：`users` 表非空时跳过，不会覆盖已有数据）。如数据库文件已存在且已有数据，初始化自动跳过；需要重置演示数据时见第 10 节。

停止：

```bash
docker compose down
```

## 3. 示例项目与场景

3 个示例项目覆盖「招募中 / 暂停招募 / 已满员」三种状态，人数与成员记录一致：

| 项目 | 发起人 | 状态 | 角色（名额） | 成员 | 申请记录 |
|---|---|---|---|---|---|
| 校园二手交易平台 | alice | 招募中 | 前端开发（2，已 1 剩 1）；后端开发（1，剩 1） | alice（发起人）、bob（前端） | bob=已通过；carol=待审核；dave=待审核 |
| 读书打卡小程序 | bob | 已暂停 | UI 设计（1，剩 1） | bob（发起人） | carol=已拒绝（含拒绝原因）；dave=已撤回；alice=待审核 |
| 考研数据可视化 | carol | 已满员 | 数据分析（1，已满） | carol（发起人）、dave（数据分析） | dave=已通过；alice=已拒绝（名额已满） |

**单名额竞争场景（验收重点）**：项目1 的「前端开发」角色上限 2 人、已有 1 名成员（bob），仅剩 1 个名额；carol 与 dave 各有一条待审核申请。发起人 alice 同时/重复接受时，最终只能有 1 人加入，另一条申请保持待审核并提示名额已满。

## 4. 核心流程验证步骤（页面操作）

1. 用 `alice` 登录 → 项目广场看到 3 个示例项目，卡片显示角色剩余名额与状态徽章。
2. 打开「校园二手交易平台」详情：可见项目介绍/目标/进展/预期成果、发起人资料、角色技能要求与剩余名额、成员名单。
3. 登录 `carol` 或 `dave` → 在项目详情选择角色、填写申请理由与可承担内容、提交 → 提示成功，状态为待审核。
4. 回到 `alice` → 项目详情/我的项目 →「管理申请」：看到待审核申请及其**申请时资料快照**。接受一条 → 成员名单和剩余名额同步更新；拒绝一条需填写原因。
5. 「前端开发」只剩 1 个名额时，尝试接受第二名申请人 → 后端返回「名额已满」，该申请保留待审核；可对其执行拒绝。
6. 登录被拒/撤回的申请人 →「我的申请」可见记录与拒绝原因；可对同一项目重新申请，旧记录保留。
7. 发起人「暂停招募」后，新申请被拒绝（提示已暂停）；已有待审核申请仍可审核；「恢复招募」后恢复申请。
8. 数据持久化见第 9 节。

## 5. 申请状态与名额计算说明

申请状态机：

```
            提交申请                发起人接受（事务内校验名额）
 (无记录) ─────────► 待审核(PENDING) ─────────────► 已通过(ACCEPTED)
                        │  │
        申请人撤回      │  └──── 发起人拒绝（需填原因）──► 已拒绝(REJECTED)
        （仅待审核）    ▼
                   已撤回(WITHDRAWN)
```

规则：

- 同一项目同一用户最多同时存在 **1 条待审核申请或 1 个已加入身份**；已加入者不能重复申请；有待审核申请时不能再次提交。
- 被拒绝或撤回后可以重新申请，旧记录永久保留（状态不变）。
- 待审核申请**不占**名额；只有「接受」成功才写入成员并占用该角色 1 个名额。
- 名额计算：`某角色剩余名额 = capacity - count(members where role_id = 该角色)`。发起人的成员记录 `role_id` 为 NULL，因此**展示为成员但不占任何名额**。
- 「接受」在同一个 SQLite 事务内完成「重新统计名额 → 写成员 → 更新申请状态」：名额已满时拒绝并返回 409，申请保持待审核；重复接受同一条已处理申请返回 409，不会重复添加成员；并发接受两人时最多 1 人成功。
- 项目展示状态：暂停优先显示「已暂停」；否则所有角色满员显示「已满员」；否则「招募中」。
- 权限（全部在后端校验，不依赖前端隐藏按钮）：仅发起人可查看本项目全部申请、接受/拒绝、暂停/恢复；申请正文仅本人与该项目发起人可见；其他用户无法读取他人申请正文。

## 6. 环境变量说明

均带默认值，可按需覆盖；**示例中不含任何真实密钥**，本应用未接入任何外部服务（如后续接入第三方服务，密钥必须通过服务端环境变量配置，不得写入仓库或前端代码）：

```bash
# 后端（backend）
PORT=3001                      # 服务端口，默认 3001
DATA_DIR=/app/data             # SQLite 数据目录，默认 /app/data（Docker 内）
DB_PATH=/app/data/teamup.db    # SQLite 文件路径，默认 <DATA_DIR>/teamup.db

# 前端（frontend，构建时注入）
VITE_API_BASE=http://localhost:3001   # 浏览器访问后端的地址，默认 http://localhost:3001

# 外部服务配置示例（本项目未使用；如接入请按此方式在服务端配置）
# THIRD_PARTY_API_KEY=your-key-here
```

## 8. Docker 部署说明

- `docker-compose.yml` 包含 `backend`（3001）与 `frontend`（3000）两个服务。
- 前端在镜像构建阶段执行 `vite build`，运行时用 `vite preview` 提供静态服务。
- 后端健康检查通过后前端才启动（`depends_on: condition: service_healthy`）。
- SQLite 数据库通过 `./backend/data:/app/data` 卷持久化。
- 验收环境无需额外安装 Node.js 或数据库：全部运行在容器内。

```bash
Remove-Item .\backend\data\teamup.db* -Force
docker compose up -d   # 首次启动自动重新执行 seed.js
```

## 11. 已知限制

- 仅本地演示规模：SQLite 单文件数据库、单进程后端，未针对高并发做优化（并发正确性依赖 SQLite 事务与唯一约束）。
- 发布后不支持修改角色名额、删除项目或编辑项目内容（按题目范围边界约定，避免把名额变更扩展为另一套流程）。
- 未实现注册、验证码、找回密码与后台管理，账号由 seed 预置。
- 头像使用昵称首字生成，无上传功能。
- 前端通过 `VITE_API_BASE` 直连后端，未做反向代理；部署到非本机时需重新构建并修改该变量。
- 鉴权为简化版 Bearer 会话令牌（存于 SQLite），未实现令牌过期刷新。

## 12. 关键场景测试与实际结果

以下结果均为本机 `docker compose up --build` 启动后的**实际运行记录**（通过后端 API 调用验证；并发场景由容器内 Node 脚本同时发起请求）。

### 场景 A：单名额竞争（并发接受 2 人）—— 核心验收项

项目1「前端开发」仅剩 1 个名额（1/2），carol 与 dave 各有一条待审核申请。发起人 alice 对两条申请**同时发起接受请求**：

| 操作 | 实际结果 |
|---|---|
| 并发接受 dave 的申请（#3） | HTTP 200，状态变为 ACCEPTED，dave 进入成员名单 |
| 并发接受 carol 的申请（#2） | HTTP 409：「角色「前端开发」名额已满，无法接受；该申请仍保持待审核状态，你可以选择拒绝它」 |
| 最终状态 | 前端开发 **2/2**，成员=鲍勃、戴夫（只加入了 1 人）；carol 的申请保持 PENDING，未出现在成员名单 |

### 场景 B：重复审核（幂等，不重复占位）

| 操作 | 实际结果 |
|---|---|
| 对已通过的申请再次接受 | HTTP 409「该申请已被处理（当前状态：已通过），不能重复操作」，成员未重复添加 |
| 对已拒绝的申请重复拒绝 | HTTP 409「该申请已被处理（当前状态：已拒绝），不能重复操作」 |

### 场景 C：申请规则、撤回与重新申请

| 操作 | 实际结果 |
|---|---|
| 申请自己发起的项目 | HTTP 400「不能申请自己发起的项目」 |
| 申请已暂停的项目 | HTTP 409「该项目已暂停招募，暂不能提交申请」 |
| 已有待审核时再次申请 | HTTP 409「你已有一条待审核申请，请等待审核或先撤回」 |
| 申请已满员角色 | HTTP 409「该角色名额已满，不能申请」 |
| 撤回待审核申请 | 200，状态变为 WITHDRAWN |
| 撤回非待审核申请（已拒绝） | HTTP 409「只有待审核的申请可以撤回」 |
| 撤回后重新申请 | 201，新申请 PENDING；旧记录（WITHDRAWN）保留 |
| 被拒后重新申请 | 201，新申请 PENDING；旧记录（REJECTED，含原因）保留 |
| 暂停项目中审核既有待审核申请 | 200，ACCEPTED，名额同步更新（暂停只拦截新申请） |
| 拒绝时未填写原因 | HTTP 400「请填写拒绝原因」 |

### 场景 D：权限与数据隔离（全部由后端校验）

| 操作 | 实际结果 |
|---|---|
| 非发起人查看项目全部申请 | HTTP 403「只有发起人可以查看本项目的申请」 |
| 非发起人接受/拒绝申请 | HTTP 403「只有发起人可以审核申请」 |
| 未登录访问任何数据接口 | HTTP 401「未登录，请先登录」 |
| 查看「我的申请」列表 | 仅返回本人记录（2 条全部属于本人），无法读取他人申请正文 |

### 场景 E：筛选（关键词、角色、技能多选、状态、组合条件）

| 筛选条件 | 实际结果 |
|---|---|
| 关键词「二手」 | 1 个：校园二手交易平台 |
| 角色「前端」 | 1 个：校园二手交易平台 |
| 技能 React + JavaScript（同一角色全部包含） | 1 个：校园二手交易平台 |
| 技能 React + SQLite（无单一角色同时包含两项） | **0 个**（验证「角色和技能必须匹配到同一个招募角色」） |
| 状态 已暂停 / 已满员 / 招募中 | 分别命中 读书打卡小程序 / 考研数据可视化 / 校园二手交易平台 |
| 角色「数据」+ 状态「已满员」（组合） | 1 个：考研数据可视化 |
| 角色「数据」+ 关键词「二手」（无交集） | 0 个 |

### 场景 F：数据持久化（保留数据卷重建容器）

新建项目「持久化验证项目」→ dave 提交申请 → alice 接受（dave 加入成员），随后执行 `docker compose down` → `docker compose up -d`（容器销毁重建）：

| 检查项 | 实际结果 |
|---|---|
| 项目 | 「持久化验证项目」仍在，中文标题无损 |
| 申请 | 申请记录仍在，状态 ACCEPTED |
| 成员 | 戴夫仍在成员名单，角色 1/1 |

### 场景 G：一键启动

`docker compose up --build` 构建成功：后端健康检查通过（healthy）后前端才启动；`http://localhost:3000` 返回 200（静态 JS 资源 200），`http://localhost:3001/api/health` 返回 `{"ok":true}`。

> 以上验证完成后已重置数据库并重新执行 seed，当前环境即为第 3 节的初始演示状态。
